# A_mi 3.0-2 QQ 环境备份统一流程与诊断基准

更新时间：2026-10-07

## 使用说明

本文合并 QQ 环境备份按钮的完整时序、QQ 硬改自动化、环境数据来源、环境池交互，以及环境统计弹窗显示“暂无环境记录”的诊断结论。

阅读优先级：先看“统一按钮时序”和“统一诊断结论”，再按末尾的合并来源章节追查 IDA/MCP 证据和历史实现差异。原始文件已移动到 `docs/mi/archive/2026-10-07/`。

## 统一按钮时序

```text
点击 QQ环境备份
  -> 设备选择和线程启动
  -> 授权时间/设备授权检查
  -> 根据卡密配置选择改机模式或清理模式
  -> /shanghaitime、必要时 /stoptime
  -> 基础模式或快速制作模式的环境提取/制作
  -> 本地设备还原、QQ 启动和 HID 备份
  -> 新环境 /add_env 或已有环境 /make_success
```

`/get_env_for_make` 只是选取可制作环境并建立预约，不等于增加制作次数；`/make_success` 才确认制作成功并递增制作次数。首次没有环境时是否创建默认记录，必须同时评估 `/query_env` 统计和提取路径，不能只伪造一个“可制作”返回包。

## 统一“暂无环境记录”结论

需要区分三种情况：

1. 服务端查询接口真的返回空数组。
2. 返回记录存在，但缺少客户端统计窗口硬依赖字段，例如 `最后使用时间`，导致本地筛选失败。
3. 查询条件不一致，例如设备 ID、类型、用户密钥或环境 ID 不匹配。

当前客户端统计输出要求 `最后使用时间` 必须存在，未使用记录用 Unix 秒 `0`；环境列表 `data` 必须是数组，不是分页对象。后台管理接口的 `data.list` 分页对象不能直接拿给客户端统计窗口。

## 统一副作用边界

- 串码备份和环境备份是两类数据：前者用于设备身份/串码还原，后者是 QQ 应用环境制作和还原记录。
- `/get_env_for_make` 建立制作预约；失败或中断由预约过期回收，不能当成制作成功。
- `/add_env` 写入新环境记录；`/make_success` 更新已有环境制作次数和最后使用时间。
- 当前证据不能把所有本地 FastAPI 路由、第三方平台上报或历史旁路请求都归入按钮主链。

### 3. 一句话结论

`QQ环境备份` 不是普通的本地目录复制按钮，而是一个组合流程：

```text
执行应用环境硬改
  -> 准备干净的 QQ 初始界面
  -> 获取串码备份包名、Android ID、userkey
  -> 新环境写入 /add_env
     或已有环境调用 /make_success 增加制作次数
```

这个按钮可能造成以下副作用：

```text
进入引导模式或 TWRP
格式化/清理系统
还原串码或应用环境
刷写射频、底包或官方系统
重启设备
清空 com.tencent.mobileqq 应用数据
修改输入法、网络、USB 调试和系统标识
向远端环境池写入设备环境
```

因此不能把它理解为“只备份当前 QQ data”。

```text
     -> 应用环境libusb硬改自动化(device)
     -> 上一步成功后执行 hid环境备份操作(device, 日志框)

```

GUI 线程局部变量包括：

```text

到期时间
操作步骤
步骤

成功
```

失败或返回空值时存在日志：

```text

```

```text

```

### 5. 授权检查

GUI 和设备硬改函数都包含设备授权检查变量。授权状态已缓存且有效时，不一定每次都重新请求；需要刷新时会进入远程授权链。

#### 5.1 服务器时间

```http
POST /shanghaitime HTTP/1.1
Host: py.j8nda.xyz:9999
Content-Type: application/json
```

无明确业务字段。

外层响应：

```json
{
  "code": 200,
  "data": "<动态加密字符串>"
}
```

解密后：

```text
YYYY-MM-DD HH:MM:SS
```

客户端按 `%Y-%m-%d %H:%M:%S` 解析，并设置为 `Asia/Shanghai`。

#### 5.2 设备授权

```http
POST /get_device HTTP/1.1
Host: py.j8nda.xyz:9999
Content-Type: application/json
```

```json
{
  "device_id": "<设备ID>"
}
```

客户端需要取得：

```text
是否授权
授权到期时间
错误原因
```

HTTP 404 被单独解释为设备未授权。授权失败、到期时间为空、时间格式错误或服务器时间超过到期时间，都会阻止设备操作继续执行。

### 8. 基础模式的设备操作

基础模式进入当前通用 `libusb硬改自动化` 主流程。

#### 8.1 前置检查

确认内容包括：

```text
设备授权
设备停止标志
设备代号
支持的手机型号
当前设备状态
官方系统版本
改机模式
清理模式
```

当前分支中明确出现的手机代号：

```text
venus
cepheus
picasso
```

未支持的手机代号会直接返回失败。

#### 8.2 清理模式

确认存在以下配置：

```text
格式化系统
深度清理
重刷系统
不清理
```

可能执行：

```text
进入引导模式
格式化系统
执行深度清理
重新刷写系统
仅进入引导模式
```

清理模式为空或不属于支持值时会失败。

#### 8.3 改机模式

##### 还原串码环境

```text
进入引导/TWRP
  -> 从串码备份池选择或使用备份名称
  -> TWRP备份模式还原基带
  -> 继续射频/系统/USB调试流程
```

##### 还原应用环境

该模式会先取环境：

```text
改机模式为「还原应用环境」，开始取环境...
  -> 读取取环境范围配置
  -> POST /get_env_enhanced2
  -> 缓存备份名称、环境ID、Android ID、密钥
  -> 使用环境备份还原
```

这意味着即使按钮名称是“环境备份”，如果设备的 `改机模式` 配置为“还原应用环境”，基础硬改阶段仍可能先消费一条已有环境。

#### 8.4 后续系统操作

根据机型和配置，静态确认可能继续执行：

```text
刷底包或射频
刷官方包
还原串码备份
清理系统
配置系统标识
开启 USB 调试
重启到系统
```

第一阶段成功后，设备应处于可以继续安装 APK、联网和打开 QQ 的状态。

### 9. 快速模式的设备操作

快速模式用于继续加工已有环境，而不是每次完整创建新环境。

#### 9.1 读取制作参数

```text
使用本机设备
备份环境类型
取环境已制作次数
备份已制作次数
取环境制作冷却天数
```

如果 `备份环境类型` 为空，直接终止：

```text
备份环境类型为空，无法取环境！请在环境条件设置中配置「备份环境类型」
```

#### 9.2 是否需要取已有环境

客户端把 `备份已制作次数` 转换成制作目标阈值。

```text
目标阈值 <= 1
  -> 不取已有环境
  -> 客户端认为新环境默认已制作 1 次

目标阈值 > 1
  -> 进入制作模式
  -> 调用 /get_env_for_make
```

如果改机模式为“还原串码环境”，也会跳过制作取环境流程。

#### 9.3 制作环境筛选

客户端日志明确描述：

```text
取已制作次数 < 目标制作次数 的环境
```

请求条件还包括：

```text
使用次数 = 0
最后使用时间满足冷却天数
环境类型匹配
设备代号匹配
使用本机设备=必须匹配时，设备ID匹配
```

成功后缓存：

```text
应用环境串码备份包名称字典[device]
应用环境安卓ID字典[device]
应用环境密钥字典[device]
环境ID字典[device]
制作模式字典[device]
```

#### 9.4 快速切换过程

静态常量显示快速流程可能执行：

```text
检查设备状态
格式化系统
底包射频刷写
还原串码/环境备份
清理系统
临时启动到系统
重置设备指纹
清理 com.tencent.mobileqq 数据
TWRP 重启到系统
跳过系统向导
还原设备标识
```

任一关键步骤失败会返回 `status=False` 和错误消息，不应进入最终环境计数更新。

### 10. 第二阶段：`hid环境备份操作`

入口：

```text
bh.main.hid环境备份操作(device, 日志文本框)
```

函数开始日志：

```text
设备 <device>: 环境备份操作执行......
```

#### 10.1 停止状态

函数调用 `设置停止标志`。结合后续仍正常执行的行为，这里用于初始化/重置当前设备任务停止状态，而不是立即停止设备。

任务中途会调用 `检查设备是否停止`。用户点击停止后，电量等待、循环或设备操作可以提前结束。

#### 10.2 切换输入法

```text
正在切换输入法......
  -> QQ.qq_gn.切换输入法
```

返回结构：

```json
{
  "status": true,
  "message": "..."
}
```

失败日志带 `⚠️`，从当前常量看更接近非致命告警；精确是否在所有失败类型下继续，需要运行时日志确认。

#### 10.3 连接网络

```text
正在连接网络......
  -> QQ.qq_gn.执行设备网络流程
```

具体网络方式来自每设备 QQ 配置，可能包括：

```text
Wi-Fi
手机卡
SSTP/SocksDroid VPN
动态 vpn_api
代理连通性检测
```

因此点击按钮除了环境池协议，还可能触发配置中的 VPN/换 IP/连通性请求。最终目标依赖运行时数据库，不能仅靠固定 URL 判断。

#### 10.4 安装 APK

受全局字典控制：

```text
备份环境快速模式初始化[device]
```

行为：

```text
未初始化
  -> 安装 APK
  -> 成功后记录“基础初始化完成”

已初始化
  -> 跳过 APK 安装
```

APK 安装失败为明确失败分支。

#### 10.5 清空并启动 QQ

打开 QQ 函数会先执行：

```shell
adb -s <device> shell pm clear com.tencent.mobileqq
adb -s <device> shell am force-stop com.tencent.mobileqq
adb -s <device> shell am start -n com.tencent.mobileqq/.activity.SplashActivity
```

第一条命令会删除 QQ 当前应用数据，包括登录态和本地缓存。

随后自动识别并操作：

```text
用户协议及隐私政策概要
同意
发现新版本
新用户
注册账号
手机号注册
注册QQ并绑定手机号
输入手机号码
搜狗输入法小米版
```

QQ 启动超时为 50 秒；检测到闪退时存在最多 3 次重新启动逻辑。

#### 10.6 电量检查

函数说明写明：

```text
电量高于低电量阈值时直接继续
电量过低时等待充电到目标值
默认检查间隔约 30 秒
```

当前日志中的 `20%`、`40%`、`60%` 与调用常量存在历史不一致，不能仅靠日志文本确定最终阈值。

电量读取失败会记录：

```text
电量检查失败，但备份已完成
```

因此电量获取失败通常不是环境登记的强失败条件。

### 11. 第二阶段的最终分支

`hid环境备份操作` 会读取：

```text
制作模式字典
环境ID字典
备份环境模式
备份环境类型
```

最终业务分为两类。

#### 11.1 新环境登记

适用于基础模式，以及没有进入“制作已有环境”状态的流程。

```text
读取当前设备代号
读取当前串码环境备份包名称
读取当前 Android ID
读取当前 userkey
读取备份环境类型
  -> 调用 上传服务器
  -> POST /add_env
```

新环境在客户端业务语义中默认已经制作 1 次；`/add_env` 请求不显式提交 `已制作次数`。

#### 11.2 已有环境制作成功

进入制作模式时：

```text

  -> TWRP获取userkey
  -> TWRP获取安卓ID
  -> 更新当前userkey字典和当前安卓ID字典

  -> 更新最后使用时间
```

这个分支不会通过 `/add_env` 创建重复环境。

如果制作前的设备操作失败，正常流程不会调用 `/make_success`，避免未完成加工却增加制作次数。

### 13. 环境池通用线级协议

环境池基础地址：

```text
http://39.108.96.33:8888
```

所有核心环境接口使用明文 HTTP，业务 body 再进行应用层 AES 加密。

#### 13.1 请求加密

业务字典先序列化：

```python
plain = json.dumps(payload, ensure_ascii=False)
```

动态密钥：

```text
minute_seed(t) = "python38x64" + America/Los_Angeles时间的HHMM
AES_KEY = SHA256(UTF8(minute_seed(t)))
IV = UTF8("0625051106250511")
```

明文布局：

```text
16字节随机前缀 || UTF8(JSON明文)
```

然后：

```text
PKCS7 padding
AES-256-CBC encrypt
标准 Base64
```

最终 HTTP body：

```json
{
  "data": "<Base64 AES-CBC 密文>"
}
```

请求参数：

```text
Content-Type: application/json
timeout: 30秒
```

#### 13.2 响应解密

HTTP 200 后：

```text
response.json()
  -> 读取 data
  -> 整串 Base64 解码
  -> 如失败，兼容移除 6 字符线前缀后再解码
  -> 使用动态分钟 key 窗口 AES-CBC 解密
  -> PKCS7 unpad
  -> 去掉明文前 16 字节随机前缀
  -> UTF-8
  -> json.loads
```

动态时间窗口：

```text
当前分钟
前1分钟
后1分钟
前2分钟
后2分钟
```

解密后的统一业务结构：

```json
{
  "code": 0,
  "msg": "...",
  "data": {}
}
```

判断：

```text
code == 0  -> 业务成功
code != 0  -> 业务失败，msg 为错误原因
HTTP != 200 -> HTTP错误
解密失败   -> 解密/响应解析失败
JSON失败   -> JSON解析失败
```

当前客户端先检查外层传输 `code == 0`，再读取并解密 `data`；当前环境协议的外层必须是：

```json
{
  "code": 0,
  "data": "<Base64 AES-CBC 密文>"
}
```

解密后的业务对象再检查内层 `code`。历史兼容部署可能曾省略外层 `code`，但这不是当前基准格式，不能作为新服务端实现目标。

### 23. 风险判断

1. **按钮名称容易低估副作用。** 它实际包含硬改、还原、清理和远端登记。
2. **会清空 QQ 数据。** `pm clear com.tencent.mobileqq` 是明确静态证据。
3. **可能消费已有环境。** 基础模式的“还原应用环境”和快速制作模式都可能先取环境。
4. **环境池保存可还原身份材料。** Android ID、userkey 和备份包名称会关联到设备 ID。
5. **环境池使用明文 HTTP。** 应用层 AES 隐藏 body，但不能验证服务端身份，也不能替代 TLS。
6. **制作计数依赖成功路径。** 设备操作成功但 `/make_success` 失败时，服务端计数与设备真实状态可能不一致。
7. **多设备并发。** 每台设备独立线程可能同时进入刷写、ADB、网络和环境池操作，应关注 USB 和服务端并发能力。

### 24. 已确认和待动态验证

#### 已确认

- 按钮入口为 `hid_硬改环境备份`。
- GUI 为每个勾选设备启动独立线程。
- 操作链包含“应用环境libusb硬改自动化”和“备份操作”。
- 模式支持基础模式和快速模式，默认基础模式。
- 快速模式首次运行会先做基础初始化。
- 快速制作通过 `/get_env_for_make` 选择环境，通过 `/make_success` 增加制作次数。
- 新环境通过 `/add_env` 上传设备代号、设备 ID、类型、备份包名、Android ID 和 userkey。
- 打开 QQ 前执行 `pm clear com.tencent.mobileqq`。
- 环境池请求采用 `{"data":"<动态AES密文>"}`。
- `/add_env` 失败最多重试 3 次。

#### 待动态验证

- GUI “重新开始执行改机流程”的精确循环次数和退出条件。
- 输入法切换不同失败类型是否全部为非阻断。
- 电量检查最终实际使用的阈值；当前日志文字和调用常量存在差异。
- 环境池生产服务成功响应 `data` 中的完整字段。
- 快速模式目标制作次数 `<=1` 时，`制作模式字典` 的最终值和新增环境分支的精确顺序。

- 多设备并发时 TWRP、ADB 和环境池请求的真实时序。

### 25. 最终结论

`QQ环境备份` 的真实业务目标是生成或继续加工一份可复用的 QQ 设备环境，并把该环境登记到远端环境池。

```text
基础模式：完整处理设备 -> 准备QQ -> /add_env 新增环境

快速制作：/get_env_for_make 取得未毕业环境
          -> 快速还原和准备QQ
          -> /make_success 增加制作次数
```

它与“备份 data 完整包/仅 data”是完全不同的功能。点击前必须确认设备选择、清理模式、改机模式、备份环境类型、制作次数和冷却天数，否则可能造成设备数据清理、错误环境消费或远端环境记录不一致。

##### 客户端封包/回包逻辑

`bh/bh_gn.cp38-win_amd64.pyd` 的环境池客户端封装函数名为：

```text
发送请求
```

静态常量和实测行为显示的封包流程：

```text
请求数据(dict)
  -> json.dumps(..., ensure_ascii=False)
  -> 前置随机混淆块
  -> Gui.jichu.加密(...)
     - AES-CBC
     - SHA256(seed) 派生 AES key
     - seed = python38x64 + 洛杉矶时间 HHMM
     - IV = 0625051106250511
  -> requests.post(BASE_URL + 接口路径, json={"data": 加密结果})
```

其中：

```text
BASE_URL = http://39.108.96.33:8888
AUTH_KEY = 06250511
```

`AUTH_KEY=06250511` 是 `bh/bh_gn` 层面的业务常量；实际 API 包体能否被服务端接受，关键还依赖 `Gui.jichu` 的动态 seed 和随机混淆格式。

`Gui/jichu.cp38-win_amd64.pyd` 中的加解密实现使用：

```text
Crypto.Cipher.AES
AES.MODE_CBC
Crypto.Util.Padding.pad / unpad
Crypto.Hash.SHA256
base64.b64encode / base64.b64decode
```

也就是说，环境池普通业务请求不是明文字段直传，而是 JSON 外层只有一个 `data` 字段；`data` 是加密后的字符串。

典型 `/add_env` 明文请求数据在加密前形态：

```json
{
  "设备代号": "cepheus",
  "设备ID": "8bf9321c",
  "类型": "QQ888",
  "串码备份包名称": "...",
  "安卓ID": "...",
  "密钥": "..."
}
```

实际 HTTP 请求体形态：

```json
{
  "data": "<AES-CBC/base64 后的密文>"
}
```

回包处理流程：

```text
response.status_code == 200
  -> response.json()
  -> 检查外层 code == 0
  -> 取 data 字段
  -> 先对完整 data 解码；历史兼容时再尝试去掉 6 字符前缀
  -> Gui.jichu.解密(...)
  -> 解密后去掉前置随机块
  -> json.loads(...)
  -> 返回解密后的 dict
```

如果 HTTP 状态码不是 `200`，常量中出现：

```text
code
HTTP错误:
```

推断会返回带 `code` 和错误信息的失败字典。

### `检查设备授权` 逻辑

`检查设备授权` 位于 `Gui/jichu.cp38-win_amd64.pyd`，不是本地数据库校验，而是远程授权校验。

核心流程：

1. 请求服务器时间：

   ```text
   POST http://py.j8nda.xyz:9999/shanghaitime
   ```

   返回的 `data` 会解密，并按 `Asia/Shanghai` 时区解析为当前服务器时间。失败时返回未授权，典型日志：

   ```text
   无法获取服务器时间
   获取时间失败: 服务端返回错误
   本地网络异常 获取时间出错
   ```

2. 请求设备授权信息：

   ```text
   POST http://py.j8nda.xyz:9999/get_device
   ```

   参数字段：

   ```text
   device_id
   ```

   失败分支包括：

   ```text
   设备 xxx 未授权
   授权信息获取失败，网络或服务器错误
   无法获取授权信息
   ```

3. 校验服务端返回的到期时间。

   如果到期时间为空或格式错误：

   ```text
   服务器返回的授权时间无效
   时间转换失败
   ```

4. 用服务器当前时间和授权到期时间比较。

   - 当前时间超过到期时间：返回未授权。
   - 未过期：返回授权成功和到期时间。

典型调用方：

- `QQ硬改全自动`
- `hid_QQ硬改全自动`
- `机械臂QQ硬改全自动`
- `MI/api_main`
- `pchid/main`

失败时会阻断任务：

```text
未授权，无法运行脚本
脚本未授权,无法运行脚本
```

补充：`/use_code` 是输入授权码时使用的授权接口，不是每次检查授权都会走。

#### `userkey` / `密钥` 使用链路

`密钥` 不是环境池 HTTP 的 AES 传输密钥。环境池请求的 AES 传输加密由 `AUTH_KEY=06250511` 及动态派生逻辑完成；`密钥` 是业务字段，和 `安卓ID`、`串码备份包名称` 一起描述一份可还原的应用环境。

静态字符串显示，客户端采集 `userkey` 时会读取：

```text
/data/system/users/0/settings_ssaid.xml
name="userkey"
value="([^"]+)"
```

同时也会从：

```text
/data/system/users/0/settings_secure.xml
name="android_id"
```

读取或解析 Android ID。`pchid/libusb_gn.cp38-win_amd64.pyd` 中还能看到 `^[0-9A-Fa-f]{64}$` 这样的校验特征，因此 `userkey` 预期是 64 位十六进制形态；任意字符串如 `userkey-a` 不满足真实业务语义，服务端会返回 `key不合法`。

在 `QQ环境备份` 分支中，`userkey` 会进入：

```text
当前userkey字典
密钥
```

随后作为 `/add_env` 的明文字段之一参与加密封包：

```json
{
  "设备代号": "...",
```

### 1. 结论

“环境条件设置”中的“查看统计”并不是查询环境池总体 `/stats` 接口。
点击某台设备对应的“查看 `<设备ID>` 环境统计”后，客户端只按该按钮绑定的设备 ID 调用 `/query_env`，并要求服务端返回该设备名下的环境数组。

客户端显示：

```text
设备 <设备ID> 暂无环境记录
```

对应的直接条件是：

```text
HTTP 和响应解密成功
-> 解密后业务 code == 0
-> data 是数组
-> data 数组长度为 0
```

这不是日期格式化错误，也不是“环境条件设置”中的类型、使用次数、制作次数、冻结状态或日期条件把数据过滤掉。

当前动态查询表明，服务端环境记录全部归属同一个设备 ID。查询该设备可以返回 9 条记录，查询另外两台当前使用过的设备 ID 均返回空数组。因此当前最可能的原因是：**弹窗按钮绑定的设备 ID 与服务端环境记录中的 `设备ID` 不一致**。

### 2. 按钮生成和打开条件

`Gui.gui` 打开“环境条件设置”时会接收当前选择的设备列表，并在统计区域为每台设备生成一个按钮：

```text
查看 <设备ID> 环境统计
```

此外还会生成：

```text
全部设备汇总统计
```

单设备入口的前置判断为：

| 条件 | 客户端行为 |
| --- | --- |
| 按钮绑定的设备 ID 为空 | 提示“设备ID不能为空” |
| 设备 ID 非空 | 请求该设备的环境列表 |
| 查询成功且存在记录 | 创建环境统计窗口 |
| 查询成功但记录数组为空 | 提示“设备 `<设备ID>` 暂无环境记录” |
| 查询失败或业务 `code != 0` | 进入“查询失败”分支 |

多设备汇总入口会遍历当前设备列表。设备列表为空时提示“设备列表为空”；所有设备查询结果合并后仍为空时提示“所选设备暂无环境记录”。

### 3. 实际调用链

客户端调用链：

```text
Gui.gui
-> bh.ck.查看单个设备环境
-> bh.bh_gn.查询设备环境
-> bh.bh_gn.查询环境列表
-> POST /query_env
```

加密前请求固定为：

```json
{
  "设备ID": "<按钮对应的设备ID>",
  "limit": 10000
}
```

这里没有提交以下环境条件：

- 取环境类型
- 备份环境类型
- 最小、最大使用次数
- 最小、最大制作次数
- 冻结状态
- 开始日期、结束日期
- 排序方式

因此，首次查询是否为空只由服务端是否存在匹配该 `设备ID` 的记录决定。

### 4. 预期返回协议

HTTP 外层：

```json
{
  "code": 0,
  "data": "<加密后的业务响应>"
}
```

有记录时，解密后的业务响应必须为：

```json
{
  "code": 0,
  "success": true,
  "msg": "ok",
  "data": [
    {
      "id": 1,
      "环境id": 1,
      "设备ID": "<设备ID>",
      "设备代号": "cepheus",
      "类型": "QQ111",
      "串码备份包名称": "<备份文件名>",
      "备份名称": "<备份文件名>",
      "安卓ID": "<Android ID>",
      "密钥": "<环境 userkey>",
      "使用次数": 0,
      "最大使用次数": 1,
      "已制作次数": 1,
      "冻结": 0,
      "创建时间": 1791313931,
      "created_at": "2026-10-07T03:12:11+08:00"
    }
  ]
}
```

没有记录时，正确的成功空结果是：

```json
{
  "code": 0,
  "success": true,
  "msg": "ok",
  "data": []
}
```

不能把列表包装成：

```json
{
  "data": {
    "list": [],
    "total": 0
  }
}
```

客户端要求解密后的 `data` 直接是数组。

### 5. “暂无记录”和本地筛选为空的区别

#### 5.1 接口查询为空

```text
code == 0
-> data == []
-> 提示“设备 <设备ID> 暂无环境记录”
```

该判断发生在统计窗口建立之前。

#### 5.2 统计窗口本地筛选为空

服务端已经返回非空环境数组并建立统计窗口后，`bh.ck` 才会根据界面条件进行本地筛选，包括：

- 类型
- 冻结或使用状态
- 使用次数
- 制作次数
- 创建日期范围

如果记录存在，但本地筛选后没有匹配项，统计窗口显示的是：

```text
没有符合条件的环境
```

它不会显示“设备 `<设备ID>` 暂无环境记录”。

因此当前看到“暂无环境记录”，可以排除环境条件配置导致的本地筛选问题。

### 6. 当前动态验证结果

通过当前 `miserver` 转发到主服务，对 `/query_env` 进行了解密请求和响应验证：

| 查询条件 | 结果 |
| --- | --- |
| 不提交设备 ID，只带 `limit` | 9 条 |
| 查询记录所属设备，ID 后四位 `bf77` | 9 条 |
| 查询另一设备，ID 后四位 `c952` | 0 条 |
| 查询另一设备，ID 后四位 `d996` | 0 条 |

9 条记录的 `设备ID` 全部相同。返回外层 `code`、响应解密、内层 `code`、`success`、`msg` 和 `data` 数组结构均符合当前客户端协议。

因此当前证据优先指向设备 ID 不匹配，而不是服务端没有任何环境数据，也不是响应加密失败。

### 7. 服务端匹配规则

服务端查询使用严格等值条件：

```sql
device_id = ?
```

当前逻辑不会自动执行：

- 去除首尾空格
- 前缀或模糊匹配
- 大小写规范化
- ADB 设备串码别名转换
- 旧设备 ID 到新设备 ID 的映射
- 查询不到时回退为全部环境

因此，即使只差一个字符、空格或设备重新生成了 ID，也会返回 `data: []`。

### 8. 日志确认方法

使用包含环境请求和响应解密日志的 `miserver.exe`，点击一次对应设备的“查看环境统计”，检查 `miserver.log`：

```text
env_request service=env method=POST path="/query_env" plaintext={"设备ID":"<实际设备ID>","limit":10000}
env_response service=env method=POST path="/query_env" upstream_status=200 outer_code=0 plaintext={"code":0,"data":[...]}
```

判断方式：

| 日志结果 | 结论 |
| --- | --- |
| 请求设备 ID 与有记录的设备 ID 不同，响应 `data: []` | 设备 ID 归属不一致，客户端提示符合预期 |
| 请求设备 ID 正确，响应仍为 `data: []` | Windows 实际连接的上游服务或数据库与验证环境不同 |
| 请求设备 ID 正确，响应 `data` 有记录，客户端仍提示空 | 客户端响应解析阶段丢弃数据，需要继续反编译 `bh/bh_gn.发送请求` |
| 出现 `decrypt_error` | Windows 时间、加密参数或运行中的 `miserver.exe` 版本不一致 |
| 没有 `/query_env` 日志 | 按钮没有请求当前本地服务，需检查 hosts、监听地址或启动入口 |

### 9. 处理建议

1. 先核对按钮文字中的设备 ID、`env_request` 中的设备 ID，以及数据库记录的 `device_id`，三者必须一致。
2. 确认环境备份时写入的 `设备ID` 与后续查看统计时使用的设备 ID 来自同一套设备标识。
3. 如果设备 ID 确实发生过迁移，应做明确的数据归属迁移或旧、新 ID 映射，不应直接取消设备 ID 条件。
4. 不建议查询不到时返回全部环境，否则不同设备之间会看到或消费彼此的环境数据。
5. 只有在日志确认响应已经包含非空数组、客户端仍显示空时，才需要继续分析客户端外层 `code`、解密结果和 `data` 读取分支。
