# A_mi 分析流程与结果标准

文档标识：`a-mi-analysis-standard`

当前基线版本：`2026-10-07.v1`

用途：规定 A_mi 后续接口、客户端行为、IDA/MCP 证据和服务端兼容实现的分析流程，以及结果文档的固定结构。此文件不按日期改名，后续更新通过 Git diff、版本号和变更记录追踪。

## 2. 每轮分析固定流程

每次新版本分析必须按以下顺序执行，不能只查看 request 函数或只看接口字符串。

### 2.1 建立版本快照

记录：

```text
分析日期：YYYY-MM-DD
样本目录：绝对路径
客户端版本/文件时间：可确认时填写
IDA 数据库：模块名和 IDB 文件
服务端/代理 commit：可确认时填写
测试环境：操作系统、Go/Python/Node 版本
```

样本文件、设备 ID、授权码、token、手机号、账号和密码不得写入文档；使用模块名、短 hash 或 `[REDACTED]`。

### 2.2 盘点模块和入口

按以下顺序扫描：

1. GUI 按钮、菜单、定时器和线程入口。
2. 授权、配置、数据库和本地服务初始化。
3. 网络请求封装函数、URL 来源和 method。
4. 解密/解包函数及其调用方。
5. 业务调用方如何读取返回字段、判断状态和触发下一步。
6. 设备动作、文件写入、数据库变化和远端副作用。

每个接口至少要追到“请求构造”和“响应消费者”两端；只找到请求构造时，不能标为硬协议。

### 2.3 分层取证

证据必须按层记录：

```text
静态模块证据：IDA/MCP 函数、交叉引用、导入、调用者/被调用者
PE 资源证据：Nuitka .rsrc/.bytecode 中的字符串、参数和路由
源码证据：miserver、server、前端和测试
动态证据：脱敏日志、mock server、调用栈、抓包和运行结果
推断：由字段命名、历史文档或兼容分支推导的内容
```

静态字符串只能证明能力或潜在路径存在；只有调用链或动态证据才能证明当前流程实际触发。

### 2.4 反推返回结构

对每个请求按以下顺序记录：

```text
HTTP method/path
请求 headers/query/body
请求封包/加密
HTTP 状态和外层 JSON
响应解密/解包
业务层 code/success/status
调用方读取的字段、类型和默认值
字段缺失时的行为
成功后的下一步和状态变化
```

必须区分：

- HTTP 成功和业务成功；
- 外层 `data` 和解密后的业务 `data`；
- 单个对象、数组、分页对象、统计对象和标量；
- `null`、空字符串、`0`、空数组和缺失字段；
- 当前主链、兼容路径、历史实现和未证实内容。

## 3. 证据等级和结论状态

### 3.1 证据等级

| 等级 | 定义 | 允许结论 |
| --- | --- | --- |
| A | 当前源码、测试或调用方直接读取/比较/遍历证明 | 当前必须满足 |
| B | IDA/MCP 调用链、PE 资源和调用方共同证明 | 当前静态确认 |
| C | 请求函数、配置、字符串或兼容分支证明，但未完成消费者闭环 | 能力存在/兼容路径 |
| D | 历史文档、旧包、经验或逻辑推断 | 待验证，不得写死 |

### 3.2 结论状态标签

每条接口或字段必须带一个状态：

```text
[CONFIRMED] 当前源码/调用方/动态验证一致
[STATIC] 静态链路确认，尚缺运行时证明
[COMPAT] 历史或兼容读取，不是当前硬依赖
[INFERRED] 推断结论，不能作为实现硬要求
[OPEN] 尚未确认，列入下一轮验证
[CHANGED] 相比上一基线发生变化
[REMOVED] 相比上一基线已不再发现或不再使用
```

## 4. 标准接口结果格式

主文档中的每个接口按以下固定顺序记录，后续版本保持字段顺序不变。

### 4.1 接口元数据

```markdown
### [状态] `METHOD /path`

- 所属模块：
- 触发入口：
- 调用方：
- 证据等级：A/B/C/D
- 首次确认版本：
- 最近复核版本：
- 当前状态：主链/兼容/历史/待验证
```

### 4.2 请求结构

必须分别记录 headers、query、form、JSON、multipart 和原始 body，不把不同层的字段混在一个表里。

| 位置 | 字段 | 类型 | 必需 | 格式/取值 | 来源 | 下游用途 |
| --- | --- | --- | --- | --- | --- | --- |
| JSON | `字段名` | string/int/bool/object/array | 是/否 | 精确格式 | 调用方/源码/推断 | 触发的业务动作 |

### 4.3 封包和解包

固定写清：

```text
明文 -> JSON 序列化 -> 编码/压缩 -> 加密 -> Base64/前缀 -> HTTP body
HTTP body -> 外层 JSON -> Base64 -> 解密 -> 去 padding/随机前缀 -> JSON
```

加密记录必须包含算法、模式、padding、key/IV 来源、随机前缀、字符编码和失败行为；缺一项就标为 `[OPEN]` 或 `[INFERRED]`。

### 4.4 返回结构

同时记录成功、业务失败、HTTP 错误和空结果：

```json
{
  "http_status": 200,
  "outer": {},
  "decoded_business": {},
  "consumer_reads": ["字段名: 类型"],
  "missing_field_behavior": "具体行为"
}
```

如果响应为纯文本、multipart、空 body 或 HTTP 204，必须明确写出，不得套用 JSON 模板。

### 4.5 调用方消费

字段表必须以实际使用为中心：

| 字段 | 类型 | 读取位置/操作 | 缺失行为 | 硬依赖状态 |
| --- | --- | --- | --- | --- |
| `字段名` | 精确类型 | 比较/遍历/显示/传给下一请求 | 异常/默认值/跳过 | 硬依赖/兼容/未证实 |

### 4.6 副作用和失败分支

固定记录：

- 数据库新增、更新、软删除和计数变化；
- 本地文件、设备属性、备份包和应用环境变化；
- 后续触发的接口或设备动作；
- 重试次数、超时、预约、幂等和回滚；
- GUI 显示、日志和静默失败行为。

## 5. 环境记录标准

环境池记录与后台管理记录必须分开描述。

### 5.1 客户端 EnvironmentRecord

至少逐字段记录：

```text
环境id / id
设备代号
设备ID
类型
串码备份包名称 / 备份名称
安卓ID
密钥
使用次数
最大使用次数
已制作次数
冻结
创建时间
最后使用时间
```

当前客户端输出的时间字段默认按 Unix 秒记录；未使用的 `最后使用时间` 为 `0`。`query_env` 无 ID 时的 `data` 是数组，单 ID 时是对象；空数组必须写成 `[]`。

### 5.2 后台管理记录

后台 `/miEnvAdmin/list` 使用明文分页对象：

```text
data.list: array
data.total: number
data.page: number
data.pageSize: number
```

后台响应不得直接当作客户端环境池响应；环境密钥不得返回给前端。

## 6. API 总表标准

每轮结果必须维护一张稳定排序的总表：

| 族 | method | path/目标 | 请求类型 | 返回类型 | 调用方硬依赖 | 副作用 | 状态 | 证据 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 授权/环境/本地/第三方 | `POST` | `/path` | JSON/表单/纯文本 | 对象/数组/分页/文本/204 | 字段列表 | 状态变化 | `[CONFIRMED]` | A/B/C/D |

排序规则：先按接口族，再按客户端实际触发顺序，最后按字典序；不要按每次发现顺序重排整张表，否则 diff 噪声过大。

## 7. Diff 规则

后续更新必须保留上一基线的章节和字段顺序，只做最小修改。

### 7.1 变更类型

| 类型 | 记录要求 |
| --- | --- |
| `ADDED` | 新增接口、字段、调用链或副作用；说明首次证据 |
| `CHANGED` | method、path、字段类型、封包、状态机或调用方发生变化；必须写 before/after |
| `REMOVED` | 不再发现或调用方不再消费；说明检查范围和证据边界 |
| `RECLASSIFIED` | 证据等级或硬依赖状态变化；说明升级/降级原因 |
| `CLARIFIED` | 仅补充解释，不改变协议；避免伪装成行为变化 |

### 7.2 变更记录模板

每次更新在主文档末尾追加一条，不修改历史记录：

```markdown
### YYYY-MM-DD `CHANGE-ID` `[ADDED|CHANGED|REMOVED|RECLASSIFIED|CLARIFIED]`

- 范围：`METHOD /path` 或模块
- before：
- after：
- 证据：源码/IDA/PE/动态/测试文件和定位
- 调用方影响：
- 服务端兼容影响：
- 验证结果：
- 未解决边界：
```

### 7.3 Diff 审查重点

每次 diff 必查：

1. method 和 path 是否改变；
2. 请求字段是否新增、删除或改类型；
3. 外层和业务层 `data` 是否改变类型；
4. 时间单位和空值语义是否改变；
5. 调用方硬依赖字段是否改变；
6. 是否新增远端写入、环境上报或隐藏旁路请求；
7. 是否把 C/D 级内容误升级为当前硬协议；
8. 是否泄露真实敏感数据；
9. 是否需要新增 golden fixture 或回归测试。

## 8. 验证清单

### 8.1 静态检查

```text
[ ] 所有相关 .pyd/.py/.go/.js 模块已盘点
[ ] IDA 函数、调用者和响应消费者已关联
[ ] PE 资源路由和参数与调用链分开标注
[ ] 未使用单纯字符串命中证明运行时调用
```

### 8.2 协议检查

```text
[ ] method/path/query/body/headers 已完整记录
[ ] 封包、解包、加密、编码和前缀已记录
[ ] 成功、失败、空结果、HTTP 错误均有样例
[ ] 返回字段类型来自调用方实际用法
[ ] 单对象、数组、分页、统计、标量没有混用
```

### 8.3 回归检查

```text
[ ] 运行相关 Go/Python/前端测试
[ ] 运行环境池和授权 golden fixture
[ ] 检查 git diff --check
[ ] 检查 Markdown fenced code block 平衡
[ ] 检查新增/删除/变化的 API 总表
[ ] 记录无法动态验证的边界
```

## 10. 后续更新格式

以后新增分析结果时，按以下顺序操作：

1. 复制本标准第 4 节的接口记录格式，补入对应主文档。
2. 更新 API 总表，但保持稳定排序。
3. 在主文档末尾追加一条变更记录。
4. 如返回类型、封包或调用方字段变化，新增或更新 golden fixture。
5. 执行第 8 节检查，并在变更记录中写明测试结果。
6. 使用 `git diff -- docs/mi` 审查本轮变化，不覆盖上一轮证据。
