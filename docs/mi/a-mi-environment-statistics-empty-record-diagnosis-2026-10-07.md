# A_mi 3.0-2 环境统计“暂无环境记录”诊断结论

日期：2026-10-07

## 1. 结论

“环境条件设置”中的“查看统计”并不是查询环境池总体 `/stats` 接口。
点击某台设备对应的“查看 `<设备ID>` 环境统计”后，客户端只按该按钮绑定的设备 ID 调用 `/query_env`，并要求服务端返回该设备名下的环境数组。

客户端显示：

```text
设备 <设备ID> 暂无环境记录
```

对应的直接条件是：

```text
HTTP 和响应解密成功
-> 解密后业务 code == 0
-> data 是数组
-> data 数组长度为 0
```

这不是日期格式化错误，也不是“环境条件设置”中的类型、使用次数、制作次数、冻结状态或日期条件把数据过滤掉。

当前动态查询表明，服务端环境记录全部归属同一个设备 ID。查询该设备可以返回 9 条记录，查询另外两台当前使用过的设备 ID 均返回空数组。因此当前最可能的原因是：**弹窗按钮绑定的设备 ID 与服务端环境记录中的 `设备ID` 不一致**。

## 2. 按钮生成和打开条件

`Gui.gui` 打开“环境条件设置”时会接收当前选择的设备列表，并在统计区域为每台设备生成一个按钮：

```text
查看 <设备ID> 环境统计
```

此外还会生成：

```text
全部设备汇总统计
```

单设备入口的前置判断为：

| 条件 | 客户端行为 |
| --- | --- |
| 按钮绑定的设备 ID 为空 | 提示“设备ID不能为空” |
| 设备 ID 非空 | 请求该设备的环境列表 |
| 查询成功且存在记录 | 创建环境统计窗口 |
| 查询成功但记录数组为空 | 提示“设备 `<设备ID>` 暂无环境记录” |
| 查询失败或业务 `code != 0` | 进入“查询失败”分支 |

多设备汇总入口会遍历当前设备列表。设备列表为空时提示“设备列表为空”；所有设备查询结果合并后仍为空时提示“所选设备暂无环境记录”。

## 3. 实际调用链

客户端调用链：

```text
Gui.gui
-> bh.ck.查看单个设备环境
-> bh.bh_gn.查询设备环境
-> bh.bh_gn.查询环境列表
-> POST /query_env
```

加密前请求固定为：

```json
{
  "设备ID": "<按钮对应的设备ID>",
  "limit": 10000
}
```

这里没有提交以下环境条件：

- 取环境类型
- 备份环境类型
- 最小、最大使用次数
- 最小、最大制作次数
- 冻结状态
- 开始日期、结束日期
- 排序方式

因此，首次查询是否为空只由服务端是否存在匹配该 `设备ID` 的记录决定。

## 4. 预期返回协议

HTTP 外层：

```json
{
  "code": 0,
  "data": "<加密后的业务响应>"
}
```

有记录时，解密后的业务响应必须为：

```json
{
  "code": 0,
  "success": true,
  "msg": "ok",
  "data": [
    {
      "id": 1,
      "环境id": 1,
      "设备ID": "<设备ID>",
      "设备代号": "cepheus",
      "类型": "QQ111",
      "串码备份包名称": "<备份文件名>",
      "备份名称": "<备份文件名>",
      "安卓ID": "<Android ID>",
      "密钥": "<环境 userkey>",
      "使用次数": 0,
      "最大使用次数": 1,
      "已制作次数": 1,
      "冻结": 0,
      "创建时间": 1791313931,
      "created_at": "2026-10-07T03:12:11+08:00"
    }
  ]
}
```

没有记录时，正确的成功空结果是：

```json
{
  "code": 0,
  "success": true,
  "msg": "ok",
  "data": []
}
```

不能把列表包装成：

```json
{
  "data": {
    "list": [],
    "total": 0
  }
}
```

客户端要求解密后的 `data` 直接是数组。

## 5. “暂无记录”和本地筛选为空的区别

### 5.1 接口查询为空

```text
code == 0
-> data == []
-> 提示“设备 <设备ID> 暂无环境记录”
```

该判断发生在统计窗口建立之前。

### 5.2 统计窗口本地筛选为空

服务端已经返回非空环境数组并建立统计窗口后，`bh.ck` 才会根据界面条件进行本地筛选，包括：

- 类型
- 冻结或使用状态
- 使用次数
- 制作次数
- 创建日期范围

如果记录存在，但本地筛选后没有匹配项，统计窗口显示的是：

```text
没有符合条件的环境
```

它不会显示“设备 `<设备ID>` 暂无环境记录”。

因此当前看到“暂无环境记录”，可以排除环境条件配置导致的本地筛选问题。

## 6. 当前动态验证结果

通过当前 `miserver` 转发到主服务，对 `/query_env` 进行了解密请求和响应验证：

| 查询条件 | 结果 |
| --- | --- |
| 不提交设备 ID，只带 `limit` | 9 条 |
| 查询记录所属设备，ID 后四位 `bf77` | 9 条 |
| 查询另一设备，ID 后四位 `c952` | 0 条 |
| 查询另一设备，ID 后四位 `d996` | 0 条 |

9 条记录的 `设备ID` 全部相同。返回外层 `code`、响应解密、内层 `code`、`success`、`msg` 和 `data` 数组结构均符合当前客户端协议。

因此当前证据优先指向设备 ID 不匹配，而不是服务端没有任何环境数据，也不是响应加密失败。

## 7. 服务端匹配规则

服务端查询使用严格等值条件：

```sql
device_id = ?
```

当前逻辑不会自动执行：

- 去除首尾空格
- 前缀或模糊匹配
- 大小写规范化
- ADB 设备串码别名转换
- 旧设备 ID 到新设备 ID 的映射
- 查询不到时回退为全部环境

因此，即使只差一个字符、空格或设备重新生成了 ID，也会返回 `data: []`。

## 8. 日志确认方法

使用包含环境请求和响应解密日志的 `miserver.exe`，点击一次对应设备的“查看环境统计”，检查 `miserver.log`：

```text
env_request service=env method=POST path="/query_env" plaintext={"设备ID":"<实际设备ID>","limit":10000}
env_response service=env method=POST path="/query_env" upstream_status=200 outer_code=0 plaintext={"code":0,"data":[...]}
```

判断方式：

| 日志结果 | 结论 |
| --- | --- |
| 请求设备 ID 与有记录的设备 ID 不同，响应 `data: []` | 设备 ID 归属不一致，客户端提示符合预期 |
| 请求设备 ID 正确，响应仍为 `data: []` | Windows 实际连接的上游服务或数据库与验证环境不同 |
| 请求设备 ID 正确，响应 `data` 有记录，客户端仍提示空 | 客户端响应解析阶段丢弃数据，需要继续反编译 `bh/bh_gn.发送请求` |
| 出现 `decrypt_error` | Windows 时间、加密参数或运行中的 `miserver.exe` 版本不一致 |
| 没有 `/query_env` 日志 | 按钮没有请求当前本地服务，需检查 hosts、监听地址或启动入口 |

## 9. 处理建议

1. 先核对按钮文字中的设备 ID、`env_request` 中的设备 ID，以及数据库记录的 `device_id`，三者必须一致。
2. 确认环境备份时写入的 `设备ID` 与后续查看统计时使用的设备 ID 来自同一套设备标识。
3. 如果设备 ID 确实发生过迁移，应做明确的数据归属迁移或旧、新 ID 映射，不应直接取消设备 ID 条件。
4. 不建议查询不到时返回全部环境，否则不同设备之间会看到或消费彼此的环境数据。
5. 只有在日志确认响应已经包含非空数组、客户端仍显示空时，才需要继续分析客户端外层 `code`、解密结果和 `data` 读取分支。

## 10. 证据边界

- 按钮文本、调用函数名、空设备提示、空记录提示和本地筛选提示来自当前 `Gui/gui.cp38-win_amd64.pyd` 与 `bh/ck.cp38-win_amd64.pyd` 静态常量。
- `/query_env` 调用链、请求字段和空数组分支来自当前 `bh/bh_gn.cp38-win_amd64.pyd` 静态分析。
- 9 条记录及按设备 ID 查询结果来自 2026-10-07 对当前主服务的动态验证。
- Windows 客户端某次实际点击提交的设备 ID，仍应以对应机器上的 `miserver.log` 为最终运行时证据。
